# Оптимизации Пульта: что измерено и что сделано

Замер от 14.10.2026, Windows 11, 24 ядра. Машину в это время грузили другие
сборки, поэтому время прыгает в 1,5-2 раза между прогонами: сравнения ниже
сделаны **попеременно** (старая сборка, новая, старая, новая - 5 кругов по 10
повторов), в таблице медиана. Числа git особенно шумные: один запуск
`git version` стоит 40-60 мс и растёт под нагрузкой.

## Как мерить

```bash
cargo build --release -p pult-core --example perf --target-dir target/perf
PULT_HOME=<корень репозитория> target/perf/release/examples/perf.exe <папка> [повторов]
```

`examples/perf.rs` печатает: время базы знаний (первая загрузка и
перечитывание), каждую часть разбора (`scan::scan_timed`) в первом и
повторных прогонах, рабочий набор, пик и частную память процесса
(`K32GetProcessMemoryInfo`), живую кучу и выделения (свой счётчик-аллокатор),
размер `Project` в JSON по полям, размер `client_bundle`, цену отпечатка и
события окна. `PERF_DUMP=<файл>` пишет результат разбора: им сверялось, что
после каждой правки результат на istok, pult и пустой папке тот же байт в
байт. `PERF_KB_HEAP=1` - сколько кучи занимает каждая часть базы.

Входы: istok (большой монорепозиторий, git не доверен:
в его `.git/config` есть `core.hooksPath`, поэтому git отдельно мерился «как
доверенный»), сам `pult`, пустая папка - пол замера.

**Пол прибора.** Первая версия замера держала две копии базы одновременно
(старая ссылка жила до конца `main`) и показывала 9 МБ кучи на базу вместо
4,6. Исправлено до сравнений; все числа памяти ниже - после исправления.

## Сделано

| Что | До | После | Как мерили | Чего это НЕ даёт |
|---|---|---|---|---|

| Уроки и `health` проверяют корень по уже прочитанному списку, а не `exists()` на каждый признак | уроки на пустой папке 5,7 мс (112 запросов к диску) | 0,2 мс | `perf`, часть `topics` | Признаки с «/» (`.github/workflows`) по-прежнему спрашивают диск |

## Измерено, но не сделано

| Что | Число | Почему нет |
|---|---|---|
| `--disable-gpu` | частная память WebView2 180 -> 115-145 МБ (GPU 85 -> 13, рендерер растёт до 40-70) | Рисование переходит на процессор: под вопросом плавность прокрутки и анимаций на больших экранах. Решение владельца |
| `--in-process-gpu` | частная 180 -> 154 МБ | Второй запуск упал (код 0xC0000409) - нестабильно |
| `--enable-low-end-device-mode` | -5 МБ, в пределах шума | Не окупается |
| `--disable-background-networking`, `--disable-component-update`, `--disable-sync` | без изменений | Окно и так не ходит в сеть |
| `opt-level = "s"` | Pult.exe 9,94 -> 7,73 МБ, pult-cli.exe 4,66 -> 4,00 МБ | Скорость ядра с `s` не замерена (сборку остановили на сворачивании работы). Пока скорость важнее - остаётся 3 |
| Сжать вшитую базу (build.rs + deflate) | JSON базы 1,42 МБ -> около 0,3 МБ сжатым: -1,1 МБ на каждый exe | В релизном архиве `knowledge\` лежит рядом с exe, вшитая копия - запасная и в память не грузится. Только размер файла |
| `client_bundle` при старте | 199-212 КБ, из них термины уроков 97 КБ; собрать 2-4 мс | Один раз за запуск - не стоит сжатия и правки интерфейса |
| `Project` по IPC | istok 423 КБ, из них `info.flags` 181 КБ (43%): у каждого скрипта полный список ключей его программы | Нужна правка `ui/`: ключи один раз на программу, у скрипта - только отмеченные. Оценка: -150 КБ на istok |
| База знаний в памяти | 4,6 МБ кучи: уроки как `Value` 2,1 МБ, программы ~1,5 МБ, регулярки 0,65 МБ; загрузка 25-40 мс | Уроки целиком нужны только команде `topic`: можно держать текстом и разбирать по запросу (-1,5 МБ), но это меняет `Kb::topic` у окна и терминала |

## Следующие шаги (не начаты)

- Замерить скорость ядра с `opt-level = "s"` и `lto = "thin"` той же парой
  сборок; решить по числам.
- `SetMemoryUsageTargetLevel(Low)` у WebView2, когда окно спрятано в трей
  (wry это умеет, нужна зависимость `webview2-com` в `app/`).
- Ключи программы один раз на программу в IPC (правка `ui/`).
- Ленивые уроки в `kb.rs` (см. таблицу выше).
- Явный `--git-dir`/`--work-tree` вместо отдельного `rev-parse` сэкономил бы
  один последовательный процесс git (~50 мс), но меняет модель доверия - это
  решение владельца и ADR, не оптимизация.
